*This note part of Firmware Development Processes*

**Versioning** is important part of Firmware, Software or Hardware developement process. Even before creating the project repository, it is essential to establish a clear strategy for tracking releases (including minor releases for testing).

During the development, releases can move rapidly, and without a clear versioning strategy, it becomes difficult to track which firmware build has been shared with stakeholders (or testers). Versioning ensures that every release is uniquely identifiable, making it possible to know exactly which features and changes are included in each build.

Many see the version as just numbers like xx.yy.bb or xx.yy.zz.bb, this is okay to use it when communicate to end-users (if you are developing device for end-users). But for firmware developement needs a lot of work with complexes features (e.g secure boot), you could have a specific versions for specific testing or specific version for specific moment in the developement cycle, so what I see that the version in just number is not enough for dev team to work perfectly. What I will suggested later is to have "a version" with humain readable to make sure that the version will not jump to places it should not (I test version should not jump to release, as the firmware in most cases is a file, it could be .bin file and it is easy to lost it in wrong place). So even for no technical people or by just see the file name, the version should help to define its place in the dev cycle, which project or device for, and when it released.  

When I wrote this suggestion I think about the version in this way: 
- the version should defines/shows which project
- the version should defines/shows which dev cycle the release created from or for
- the version should defines/shows the end-user version
- the version should defines/shows the critical features (e.g secure boot)
- the version should defines/shows when the release created
- the version should defines/shows from where the released created (the commit) but I end move this to "the release notes" as no one will use it from the version itself but need to read "the release notes" to get it. 

For these points, I suggest this Versioning identifier:

Project-Branch-MAJOR.MINOR.PATCH-build-Flags-DATETIME

* **Descriptions of version parts**  
-- **Project:** Defines which project/product/device related to this firmware  
-- **Branch:** Defines which point this firmware in the lifecycle of the project/product/device firmware  
-- **MAJOR.MINOR.PATCH:** Defines the version of the firmware  
-- **build:** ensures that each build has a unique version number  
-- **Flags:** Defines the principal configs this firmware effected  
-- **DATETIME:** The date and/or the time when this firmware released  
  
Examples:  
-- iotgateway-dev-1.4.233423-5345435-s1f1l0-040120242323  
-- temperaturesensor-release-1.4.233423-5345435-s1f1l0-040120242323

Then now, how we should use each part?

* **How to use Project**

The project should include the project name, product name, or device name. It could include the processor or microcontroller name, or even the hardware version. This practice to ensure the compatibility of the firmware with the hardware.

* **How to use Branch**

The versioning should aligns with the different stages of development, this point can summarize in this table: 

| Branch Name | Branch | Example|
| -------- | -------- | -------- |
| development| dev | iotgateway-dev-1.4.23-535-s1f1l0-04012024 |
| Feature/[Feature] | Feature-Featurename |iotgateway-feature-wifi-1.4.22-55-s1f1-04012024|
| testing | test | iotgateway-test-1.4.233423-5345435-s1f1l0-04012024|
| Prerelease or Staging  | prerelease or alpha or beta | iotgateway-beta-1.4.3-55-s1f1-04012024 |
| release  | release | Example|
| hotfix/[version]  | hotfix | Iotgateway-hotfix.13-1.4.233423-5345435-s1f1-04012024|
| maintenance/[version] | maintenance | Iotgateway-maintenance.54-1.4.2-35-s1f1-04012024|


* **How to use MAJOR.MINOR.PATCH**

Each part of the version number signifies a different level of change in the codebase. This is suggestion when you need to update each part:

-- **MAJOR**  
When there are breaking changes and high risk updates.  
When there are Compiler, framework,  or Library API changes.  
When there are software architectural changes that may affect the overall compatibility with other components or devices.  

-- **MINOR**  
When there are non-breaking features and medium risk updates.  
When there are new functionalities but are still compatible with the existing system.  

-- **PATCH**  
When there are non-breaking changes and lowest risk update.  
When there are bug fixes or small improvements, but do not introduce new features but fix existing issues.  

* **How to use build**

Using build numbers is a common practice to uniquely identify different builds of the firmware. The build number is often an incremental value that helps track the progression of the firmware during development.  
For any release, even for the testing, this value should be incremented. It could be also have separate build number for release and test, or can the build number reset (move to zero) after it moved to release state. 

* **How to use Flags**

The flags use to provide a control over specific functionalities. These flags allow developers to customize and configure certain features according to firmware life-cycle and target systems. For example, you can test firmware without enable the secure boot, then when you did the full testing you can enable it, then you will have two different firmware types this can separate by "the flags". 

Example of flags:

| Functionality | Code | Options | Example |
| -------- | -------- | -------- | -------- |
| Logging/Trace via Serial (RX/TX) | L | Enable => 1 or Disable => 0 | L1 or L0 |
| Secure Boot | S | Enable => 1 or Disable => 0 | S0 or S1 |
| Flash Encryption | F| Enable => 1 or Disable => 0 | F0 or F1 |

* **How to use DATETIME**  
To represent the date "04 Jan 2026" follow this format: "DDMMYYYY" resulting in "04012026", if you want to use the date and time (e.g 12:01), use this formwate: DDMMYYYYHHMM resulting in 040120261201

* **Should we communicate this to the end-user**  
If you release firmware to end-user (person or company), it is okay to use this version, but to make it sample you can remove the project, the branch, and the flags, as he end-user will have hardware and this hardware have serial number or model name and it can replace the project, and the end-user should have only firmwares from release branch and should have specific flags. But you could keep these to have more ways to debugging in case of problems. Like a end-user  installed a firmware should not flashed in a device then you want to know offline and without anything information about it, if it is the right firmware flashed or it is not (like flashing test version instead of released version)
